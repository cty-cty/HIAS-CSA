## 1. 文档目的

本文档集中记录本轮“培养方案规则修正、选课学分逻辑优化、春季计划课程可信度管理、培养体检与智能推荐升级”的修改内容和验收结果，作为后续维护、数据更新和发布前复核依据。

本轮目标不是生成一份虚构的 2027 年春季正式课表，而是让系统能够根据正式培养材料，形成“培养方案明确的春季计划课程数据”。春季正式课程的时间、班次、教室、容量和最终开设情况，仍以届时教务系统为准。

本文件同时是项目的主修改优化记录。后续每次涉及规则、课程数据、培养方案、推荐逻辑、界面、兼容性或测试的增量修改，都必须在本文档末尾追加一条带日期的记录，不能只在代码中修改而不留说明。每条记录至少说明：修改背景、涉及文件、原有问题、实现逻辑、用户可见变化、旧数据兼容性、测试结果、本地预览状态和仍待学院/教务确认的事项。

## 2. 总体修正结论

- 课程官方属性、培养方案认定、当前学期要求和网站推荐策略已经分层处理。
- 在原有四层之前增加了 `rawSources → sourceReconciliation`：只裁决字段来源和冲突，不承担培养方案业务判断。
- 本专业明确的核心课、专业课可以按培养方案计入专业学位课；其他专业的专业类核心课和专业课可以作为专业学位学分补充，但不能替代本人专业必须完成的“核心 2 门 + 专业 2 门”。
- 非本专业专业类课程不再被直接判定为“不能作为学位课”。有同一专业学位领域依据的课程进入 `approval_required`，无明确培养方案依据的课程进入 `verification`；两者都可展示和规划，但不会增加已确认专业学位学分或替代本人专业 2+2。
- HIAS 讲堂和科学前沿讲座已分开归类，分别进入公共选修和专业非学位统计。
- 公共选修体系明确为“普通公共选修 2 学分 + 创新创业 1 学分 = 合计 3 学分”，避免把创新创业重复计算成额外的 1 学分要求。
- 历史课程、跨学期培养进度、当前学期学分和春季计划课程不再混成一个数字。
- 春季计划课程带有 planned 状态，不参与精确时间冲突、教室、容量、名额和班次判断。
- 培养方案进度不足和本学期选课错误分开显示，核心课 1 / 2 等后续学期缺口不再自动显示为本学期红色错误。
- 推荐系统以培养缺口为共同数据源，先执行硬约束过滤，再进行有限宽度的软排序和方案生成。

## 3. 规则架构

系统内部按以下四层组织，所有学校规则由确定性代码执行：

### 3.1 officialClassification：课程官方属性

优先解析课程编号第 14 位；编号缺失或无法解析时才回退到 category 字段：

| 编号类别 | 官方含义 | 是否具备专业学位课资格 |
|---|---|---|
| 1 | 学科核心课 | 是 |
| 2 | 专业核心课 | 是 |
| 3 | 专业课 | 是 |
| 4 | 研讨课 | 否，仅非学位课程 |
| 5 | 实验课 | 否，仅非学位课程 |
| 6 | 实践课 | 否，仅非学位课程 |
| 7 | 科学前沿讲座 | 否，仅专业非学位 |
| B | 公共必修课 | 不作为专业学位课 |
| X | 公共选修课 | 不作为专业学位课 |

### 3.2 programRecognition：培养方案认定

统一认定状态：

- `eligible`：正式材料足够确认符合当前培养方案。
- `approval_required`：课程官方属性允许作为专业类课程，但是否按本人培养方案认定需要导师或学院确认。
- `verification`：数据或正式材料之间存在不一致，暂时不能自动得出确定结论。
- `ineligible`：学校规则明确禁止该课程作为目标课程性质，例如研讨、实验、实践和科学前沿讲座不能设置为专业学位课。

只有 `eligible` 自动增加“已确认完成”的核心/专业门数和专业学位学分。`approval_required` 和 `verification` 课程可以选择、可以计入计划合计，但不会自动完成本人培养方案的确定性要求。

### 3.3 semesterRequirement：当前学期要求

本学期检查只处理本学期必须处理的事项，例如：

- 当前有效学分是否达到学期最低要求；
- 课程时间冲突和重复教学班；
- 2026 级一年级秋季必修是否漏选；
- 非学位课程是否被错误设置为学位课；
- 体育公共选修是否超过 1 门。

培养方案总进度不足属于黄色或绿色的“培养方案进度”，不直接作为本学期错误。

### 3.4 recommendation：网站推荐策略

推荐排序属于工具策略，不伪装成学校规定。推荐可以考虑培养缺口、课程机会成本、时间集中程度、考核压力、周末课程数量和用户偏好，但所有硬规则都在推荐打分前执行。

## 4. 选课学分统计逻辑

### 4.1 三种时间范围

培养设置页面同时理解三种范围：

1. 历史已修：用于保留既往完成记录和避免重复计分。
2. 所有学期已选/计划：用于计算培养方案总体进度、预期累计学分和分类学分。
3. 当前学期：用于本学期最低学分、冲突和当前选课提醒。

因此，秋季已经选过的课程不应在切换到春季后从培养计划总进度中消失；它们会保留在“所有学期累计”和历史/计划记录中，只是不再作为春季当前学期课程显示。春季课程数据是新增候选，不覆盖秋季记录。

### 4.2 专业学位课

分类学分中的“专业学位课”按下式解释：

```text
专业学位规划合计
= 本专业培养方案明确课程中已设置为学位课的学分
  + 非本专业专业类核心课/专业课中已设置为学位课的学分
```

例如：已确认的本专业学位课 8 学分，另有非本专业专业类课程 6 学分，则分类卡片显示：

```text
专业学位课 8 / 12 学分
已确认 8 / 12；非本专业的专业类课程 +6 学分，规划合计 14 学分（待确认，不触发培养要求完成）
```

这里的 18.5 是选课方案中的专业学位规划合计，不代表 18.5 学分全部已经被学院最终审核确认。本人专业核心 2 门和专业 2 门仍然是必须满足的自身专业课程结构要求；跨专业课程可以补充学分，不能替代这四门本专业课程。

页面提示应使用“非本专业的专业类课程”这一说法，不再使用容易误解的“待确认补充学分”。提醒应明确：建议根据学校官网、学院培养方案和教务系统正式材料确认是否可以设置为学位课；工具不能代替学校认定，所有课程安排也建议与本人导师确认是否合理。

### 4.3 核心课、专业课门数

核心课和专业课门数只统计同时满足以下条件的课程：

```text
designation === "degree"
AND recognition === "eligible"
AND 官方课程类别属于 1 / 2 / 3 中对应类别
AND 按 canonicalCourseId 去重
```

approval_required 和 verification 课程可以在列表中展示，但不能自动增加确定完成的核心/专业门数。

专业学位要求不是“学分达到 12 就完成”，而是同时检查：

```text
专业学位学分 >= 方案要求
核心课门数 >= 核心课最低门数
专业课门数 >= 专业课最低门数
specialRules 全部满足
```

### 4.4 公共选修体系

专硕公共选修采用以下口径：

```text
普通公共选修 >= 2 学分
创新创业 >= 1 学分
公共选修体系合计 >= 3 学分
```

创新创业 1 学分已经包含在公共选修体系 3 学分之内，不是“公共选修 3 + 创新创业 1 = 4”。UI 分别展示普通公共选修和创新创业，是为了让用户看清构成；总要求用“公共选修体系 3 学分”解释，避免重复理解。

### 4.5 特殊课程归类

| 课程 | requirementType | degreeRole | 计入 | 不计入 |
|---|---|---|---|---|
| HIAS 讲堂 | `publicElective` | `nonDegree` | 公共选修体系 | 专业非学位、秋春最低有效学分 |
| 科学前沿讲座 | `professionalElective` | `nonDegree` | 专业非学位/专业选修 | 公共选修、秋春最低有效学分 |
| 工程伦理 | 公共必修 | `nonDegree` | 工程硕士公共必修非学位 | 专业学位课 |

HIAS 历史记录进入公共选修统计；科学前沿讲座历史记录进入专业选修/专业非学位统计。HIAS 和科学前沿不再共用同一种培养学分类别。

### 4.6 学期最低有效学分

秋季和春季原则上分别检查有效选课学分是否达到 10 学分；夏季按适用规则处理。HIAS 讲堂和科学前沿讲座不计入这一最低有效学分，但总选课学分仍单独展示。

## 6. 春季课程可信度和正式课表升级

没有正式课程编码或排课信息时，计划课程使用独立内部 `id`，不把 `SP2027-xxx` 显示为学校正式课程编码。典型计划数据使用以下语义：

```text
scheduleStatus: "planned"
dataStatus: "planned_course"
officialCode: null
schedules: []
capacity: null
enrolled: null
```

未知时间显示“待春季正式课表公布”，不填写假的星期、节次、周次、教室、容量、已选人数或考试方式。计划课程允许用于判断培养要求能否合理留到春季、跨学期规划和机会成本分析；禁止用于精确冲突、班次、教室、容量和名额判断。

未来导入春季正式 JSON 时，按以下顺序匹配并升级原计划课程，避免两份课程重复显示：

1. `officialCode`；
2. `canonicalCourseId`；
3. 标准化课程名称 + 所属专业。

匹配成功后，`planned_course / planned` 升级为 `official_schedule / confirmed`，并补充正式编码、班次、时间、周次、教室、容量、教师和考核方式。

## 7. 专业学位、AI 和博士规则

### 7.1 跨专业专业类课程

其他专业的官方 1 / 2 / 3 类核心课和专业课，可以作为专业学位学分的补充，并在分类学分中直接加入“专业学位规划合计”。但推荐系统默认优先使用本人专业明确课程池，且跨专业课程不能代替本人专业核心 2 门和专业 2 门。

页面提醒列出具体课程名称，例如“广义相对论、半导体器件物理学”，并建议用户到学校官网、学院培养方案和教务系统确认；同时说明所有课程安排建议与本人导师确认。网页只能提供提醒和确定性计算，不能代替导师或学院作出认定。

### 7.2 人工智能特殊规则

AI 专业特殊规则已从单纯 note 文案改为通用 `specialRules` 规则评估器：有效核心学位课中，《高级人工智能》和《自然语言处理》至少 1 门。该规则和核心 2 门、专业学位学分要求同时检查，不在 UI 中散落大量专业名称判断。

### 7.3 博士培养类型

系统区分 `general_phd`、`direct_phd` 和 `combined_phd`。普通招考博士不再被错误统一套用“核心 2 + 专业 2”。学院已明确的物理电子学博士目标按总学分不少于 38、公共必修不少于 11、专业学位课不少于 16、公共选修不少于 2 计算；具体博士核心课/专业课门数和不同培养类型课程结构仍使用 verification。

## 8. 培养体检与智能补全方案

### 8.1 三类结果

- 红色“本学期必须处理”：冲突、重复教学班、有效学分不足、一年级秋季必修漏选、体育公选超额、非法设置学位属性等。
- 黄色/绿色“培养方案进度”：核心 1 / 2、专业 1 / 2、专业学位 8 / 12 等后续进度，提示“后续学期仍需完成”或“春季可继续完成”。
- 黄色“待确认事项”：approval_required、verification 和跨专业专业类课程，必须显示具体课程名称和确认建议。

### 8.2 统一培养缺口

`calculateProgramGaps(...)` 是体检和推荐共同使用的计算来源，统一输出学期学分、公共必修、核心课、专业课、专业学位、专业非学位、公共选修、创新创业和 specialRules 缺口。推荐系统不再自行复制一套培养规则。

### 8.3 推荐方案生成

用户当前已选课程默认视为锁定条件，推荐不能静默删除。算法流程为：

1. 读取已选课程和 `calculateProgramGaps`；
2. 生成本人专业明确课程、春季计划课程和可选扩展课程候选；
3. 先过滤未开课、层次不适用、时间冲突、重复课程、用户排除课程和明确不合格课程；
4. 再按培养缺口、特殊规则、当前学期必要性、秋春机会成本、时间安排、考核压力和用户偏好排序；
5. 使用有限宽度/有限迭代启发式搜索，最多生成培养要求优先、课业均衡、时间集中等 2—3 个明显不同方案；
6. 应用前展示新增课程、换班课程和可能的移除课程，必须由用户确认。

approval_required 课程默认不用于补齐确定的专业学位硬缺口；只有用户主动开启扩展候选时才显示，并标明“该课程尚不能由本工具确认计入培养方案”。

### 8.4 边际贡献与过度选课

每门候选课程计算核心缺口、专业缺口、专业学位学分、学期学分、特殊规则和过度满足情况。核心已达到 2 / 2 或专业已达到 2 / 2 后，新增同类课程不再继续获得“补缺口”最高奖励，改按研究方向、兴趣、课程质量和时间安排考虑，避免自动生成过多核心课和专业课。

### 8.5 班次处理

教学班不是独立培养课程。同一课程的 01、02 班使用同一 `canonicalCourseId`，推荐会先尝试不冲突班次，再把选中的班次作为可替换 section。用户仍可手动换班。

## 9. 课程去重与冲突逻辑

课程编号存在时，去掉末尾班次后缀形成 `canonicalCourseId`。例如：

```text
280216010108MB001-01
280216010108MB001-02
        ↓
280216010108MB001
```

编号缺失时，回退到标准化课程名称 + 所属专业；英语课程继续保留现有 family 识别逻辑。该标识统一用于重复选课、推荐去重、培养方案计数、历史课程去重、换班和一年级秋季必修检测。

课程冲突必须同时满足：同一天、节次有交集、教学周有交集。相同时间但教学周不交叉的课程不判定为冲突。

## 10. 兼容性保证

本轮保持以下功能和旧数据兼容：

- 旧 localStorage 中的已选课程、designation、培养方向、历史课程和英语免修状态；
- 多学期隔离以及秋季历史记录在春季总进度中的保留；
- 旧备份导入与恢复；
- 培养方案导入，缺少 `specialRules` 等新字段时使用安全默认值；
- 英语免修后 3 学分计入、已选英语不重复计分、历史英语不重复；
- 课程搜索、筛选、详情、冲突检测、按周查看、换班、撤销、清空；
- 课程数据更新、WakeUp CSV 导出格式、离线 HTML 和 GitHub Pages。

新增字段均采用可选或安全默认设计，没有使用 `localStorage.clear()`，也没有删除既有课程数据。

### 15.1 2026-09-09：培养方向筛选增加可扩展的学院一级分组

#### 修改背景

原有课程筛选中的“按所属学科或专业筛选”是扁平列表。此前为物光学院增加分组时，如果继续在页面中直接写死学院名称，未来加入其他学院和专业后，需要反复修改 UI 条件，容易造成分组遗漏、重复维护和不同入口显示不一致。

本次修改的目标是把学院分组变成培养方案数据的一部分，使“培养设置”与“课程学科/专业筛选”共同读取同一套分组信息。

#### 涉及文件

- `app/program-plans.ts`：为培养方案增加可选 `college` 字段，并提供通用的学院归组函数。
- `app/course-explorer.tsx`：培养设置和课程筛选均改为读取动态学院分组；导入方案缺失学院字段时执行安全回退。
- `scripts/validate-rules.mjs`：增加内置方案归组、旧方案回退和新增学院自动生成分组的回归断言。
- `README.md`：补充培养方案 JSON 的 `college` 字段和扩展方法。

#### 具体实现

1. `ProgramPlan` 增加可选字段 `college?: string`。当前物光学院内置方案统一填写 `物光学院`，包括物理电子学学硕、光电信息工程专硕、人工智能专硕、材料工程专硕及物理电子学不同博士培养类型。
2. 新增 `getProgramPlanCollege()`，统一处理学院名称为空或缺失的情况；缺失时使用“其他培养方案”。
3. 新增 `groupProgramPlansByCollege()`，按培养方案数据的学院字段生成一级分组，不在页面中硬编码学院列表。
4. 课程筛选根据当前可用的内置方案和已导入方案动态建立专业归属分组。当前四个培养方向显示在“物光学院”下，未被培养方案识别的学科/专业显示在“其他学科/专业”下。
5. 课程筛选保留当前学期数据隔离；即使某专业在当前学期没有课程，仍可显示为已支持的培养方向，选择后由课程列表反馈当前学期没有匹配课程，不会跨学期串入课程。
6. 培养方案导入继续兼容旧 JSON。`college` 不是必填字段，旧方案不会因缺少学院信息而导入失败。

以后增加新学院时，内置或导入的培养方案只需增加类似字段：

```json
{
  "program": "化学工程",
  "college": "化学与化工学院"
}
```

同一学院下可以继续放置多个专业、学位类型和培养阶段。页面会自动生成“化学与化工学院”一级分组；各方案仍通过自己的 `id` 单独保存和计算，不会把同学院不同专业的培养要求混在一起。

- 当前物光学院分组包含：物理电子学、光电信息工程、人工智能、材料工程。
- 不改变已有培养方向的保存值、课程筛选值、已选课程、历史课程或导出格式。

- `npm run lint`：通过。
